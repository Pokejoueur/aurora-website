# ADR-001: Aurora Website architecture

- **Status:** Accepted
- **Decision date:** 2026-11-02
- **Scope:** Aurora Website
- **Implementation status:** Designed; not implemented

## Context

Aurora Website is the public-facing entry point for Aurora OS, Aurora Browser, and the wider project. It must provide product information, technical documentation, project maturity information, and a traceable changelog.

The site should remain maintainable at zero mandatory service cost where practical. It must not expose private repositories, credentials, or unverified claims. The repository is the sole authoritative project record for the website.

## Constraints

- Static delivery is preferred; no application backend is required for the initial release.
- English is the launch language. French may be introduced later, once translations are available and validated.
- Documentation belongs to the main website and shares its design system.
- Search is required for V1 without a mandatory hosted search service.
- Public maturity claims must be traceable to evidence.
- Changelog entries cover official releases and meaningful technical milestones, not every commit.
- Dependencies and infrastructure should be minimal and free-tier compatible where practical.
- Private Aurora repositories must never be exposed through frontend code or client-side credentials.

## Decision

### 1. Application architecture

Use **Astro with TypeScript in strict mode**, rendered using **static site generation (SSG)**.

Use native CSS and design tokens initially. Add Astro Islands only where client-side interaction is justified. Do not introduce React by default.

### 2. Internationalization and routing

Use Astro internationalization routing with:
- English (en) as the default locale.
- French (fr) as the additional planned locale.
- Explicit locale prefixes for both locales.
- The root route redirecting to /en/.

English is the only launch language. French routes and content must not be fabricated or silently populated with English fallback content. A French page is publishable only after its translation has been written and validated.

Use a stable translationKey to associate actual translations. Display a language switch only when the corresponding translation exists.

Localized pages must provide correct document language, canonical URL, reciprocal hreflang links only for existing translations, localized metadata, and sitemap entries.

### 3. Documentation

Documentation is part of the same website, repository, design system, and deployment pipeline. It is exposed under localized /docs routes and uses a dedicated layout.

Use Markdown content collections with validated metadata, including title, description, translationKey, locale, section, status, and lastUpdated.

A documentation framework such as Starlight may be evaluated later, but it is not a dependency for the initial foundation. Adopt it only if a prototype demonstrates that routing, search, and visual integration meet project requirements.

### 4. Search

Use **Pagefind** for V1 search. Generate the index during the static build. Search must be client-side, full-text, and separated by locale so results do not mix languages. Include useful excerpts and section context.

No hosted search backend is required.

### 5. Project status registry and evidence

The website repository is the authoritative source for public project status records. Keep a versioned, schema-validated registry in this repository.

Allowed status values:
- implemented
- tested
- integrated
- prototype
- designed
- planned
- blocked
- not-verified

Status definitions and evidence requirements:

| Status | Minimum meaning |
|---|---|
| implemented | An identifiable implementation exists. This alone does not imply tests pass or integration works. |
| tested | Relevant, identifiable tests have been executed and their results can be verified. |
| integrated | Functional integration with the relevant product or subsystem is demonstrated by evidence. |
| prototype | A functional experiment exists; its limitations and non-production status are documented. |
| designed | A specification or architecture decision is documented; implementation is not implied. |
| planned | An approved future item is recorded. |
| blocked | A concrete blocker and the dependency preventing progress are identified. |
| not-verified | Available evidence is insufficient to assign a more precise status. |
| verified | Explicit acceptance criteria have been satisfied, with traceable evidence showing scope, environment, date, and limitations. Verification is stronger than merely having executed tests. |

Every public status record must include a traceable evidence reference, a verification date, and enough context to understand what was verified and what was not. Records marked `verified` must additionally state the acceptance criteria that were satisfied. Do not infer status from filenames, documentation claims, or source-code presence alone.

Only intentionally public information belongs in this registry. Never put private repository contents, secrets, access tokens, or sensitive operational details in it. The public website must not require access to private Aurora repositories.

### 6. Changelog

Maintain a curated changelog covering official releases and significant technical milestones. Do not generate a public entry for every commit.

Each entry must identify its scope and link to verifiable evidence such as a release, merged pull request, or relevant repository change. A planned or discussed feature is not a completed milestone.

Changelog maintenance is performed during active project work; no autonomous background monitoring is assumed.

### 7. Delivery and hosting

Use GitHub Actions for validation and build automation. A static hosting provider such as Cloudflare Pages may be evaluated, with free-tier limits and deployment constraints verified before adoption. Hosting selection is not finalized by this ADR.

No paid mandatory service is required for the initial architecture. A custom domain may have a separate cost and is not assumed to be free.

### 8. Security and quality

- Never embed private repository credentials or tokens in client-side code.
- Treat external content and dependencies as untrusted.
- Keep dependencies minimal and review their purpose.
- Use HTTPS in production and configure an appropriate Content Security Policy and security headers.
- Do not publish downloads unless artifact provenance and integrity can be verified. Publish SHA-256 hashes and signatures when release infrastructure supports them.
- Target WCAG 2.2 AA accessibility.
- Target Core Web Vitals: LCP <= 2.5 s, INP <= 200 ms, CLS <= 0.1.

These are design requirements and targets, not claims that the current repository satisfies them.

## Alternatives considered

| Alternative | Decision |
|---|---|
| Next.js | Not selected for the initial site; the required experience does not justify its additional application complexity. |
| React + Vite | Not selected; Astro's content-oriented static architecture is a closer fit. |
| Starlight | Deferred until a focused prototype validates integration with the main website. |
| Hosted search service | Rejected for V1 because static Pagefind search avoids a mandatory external service and backend. |
| Backend/CMS | Not required for the initial content and governance model. |

## Consequences

### Positive
- Static delivery reduces operational complexity and attack surface.
- Documentation and product pages share one design system and deployment pipeline.
- Search does not require a hosted backend.
- Evidence requirements make public maturity claims auditable.
- The architecture remains compatible with zero-cost infrastructure where provider limits permit.

### Trade-offs and risks
- Static content changes require a repository change and a new build/deployment.
- Translation availability must be managed explicitly.
- Pagefind indexes must be regenerated and checked as part of builds.
- Public evidence may lag behind private implementation unless deliberately maintained.
- Provider free tiers and deployment behavior must be verified before production adoption.

## Reversibility

Content must remain separate from presentation so layouts and frameworks can evolve without rewriting project records. Stable content identifiers and translation keys should be preserved.

The locale-prefixed URL scheme is structurally significant and must be implemented consistently before public launch.

## Validation criteria

This decision is not considered implemented merely because this ADR exists. During implementation, validate at minimum:
1. A clean install and reproducible static build.
2. Explicit /en/ and /fr/ routing behavior, with no fabricated French content.
3. Correct canonical and hreflang behavior for translated page pairs.
4. Documentation collection schema validation and localized navigation.
5. Search indexing and locale isolation in a production build.
6. Status registry schema validation and rejection of entries without required evidence.
7. Changelog entries linked to verifiable project events.
8. Accessibility, security headers, and Core Web Vitals against the targets above.

## Decision record

This ADR records an accepted architectural direction. It does not establish that any website feature has been implemented, tested, integrated, or deployed.
